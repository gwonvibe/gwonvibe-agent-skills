# Behavioral Science

고객의 마음을 단정하지 않고, 관찰된 행동에서 확인 가능한 설명을 만드는 스킬이다.

## 먼저 구분할 것

- **확인된 사실:** 로그, 설문 원문, 인터뷰 발언, 실제 행동처럼 직접 확인한 정보
- **가능한 설명:** 사실을 설명할 수 있지만 아직 검증되지 않은 가설
- **모르는 것:** 자료가 없거나 서로 다른 설명을 구별할 수 없는 부분

기능 오류·가격 노출 문제·필수 정보 누락처럼 직접 확인 가능한 원인이 있으면 심리 가설보다 먼저 다룬다. 일부 집단의 기록을 전체 고객의 상태로 확대하지 않고 대상·단계·기간·분모를 보존한다.

## 작업 순서

1. 사용자가 알고 싶은 행동과 현재 자료를 확인한다.
2. 고객이 어느 단계에서 무엇을 했거나 하지 않았는지 한 문장으로 적는다.
3. 직접 확인된 원인과 아직 모르는 원인을 나눈다.
4. 추가 설명이 필요할 때만 `references/hypothesis-guide.md`에서 근거와 맞는 가설을 1~2개 고른다.
5. 각 가설과 경쟁 설명을 구별할 수 있는 가장 작은 확인 방법을 정한다.
6. 분석 요청만 받았다면 구현·문구·가격을 임의로 바꾸지 않는다.

## 경험 설계 경계

- 개인화·질문·탐색은 고객의 이해나 실제 사용 가치에 도움이 될 때 선택적으로 제공한다.
- 빠르게 끝낼 수 있는 흐름에 몰입을 이유로 필수 단계나 대기를 추가하지 않는다.
- 선택 기능에는 찾기 쉬운 건너뛰기와 되돌리기를 유지한다.
- 보안·결제·필수 정보 확인처럼 기능과 안전에 필요한 절차는 단순한 마찰로 취급하지 않는다.
- 질문하거나 직접 만들게 하는 방식의 효과도 가설이다. 모든 고객에게 같은 방식을 강제하지 않는다.

## 참조 선택

- 가설 선택과 구별 기준: `references/hypothesis-guide.md`
- 가치·탐색·참여 경험을 살필 때: `references/value-and-participation.md`
- 인터뷰에서 “원하지만 피하고 싶은 것”을 함께 찾을 때: `references/conflict-hypothesis.md`

## 출력

요청 범위에 맞게 다음만 제시한다.

1. 확인된 사실
2. 가능한 설명과 그 근거
3. 아직 모르는 것 또는 경쟁 설명
4. 다음 확인 방법 하나

미측정 효과를 전환 증가·충성도 향상으로 확정하지 않는다. 단순 문구 요청은 직접 처리하고 전체 고객 경험 진단으로 확대하지 않는다.

## 요청 예시

- “가입자 40명 중 15명이 첫 설정 화면에서 나갔어. 확인된 사실과 가능한 원인을 나눠줘.”
- “고객 인터뷰에서 ‘자동화하고 싶지만 통제권을 잃기는 싫다’는 말이 반복됐어. 어떤 가설을 세우고 무엇을 확인해야 해?”
- “직접 고르게 하는 화면이 정말 도움이 되는지, 빠른 기본 경로와 비교할 방법을 정해줘.”
