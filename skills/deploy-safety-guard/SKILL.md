# 배포 안전 점검

빌드가 성공했다는 사실과 실제 서비스가 안전하게 동작한다는 사실을 구분한다. 변경 범위와 실패 비용에 맞는 항목만 확인하고, 확인하지 못한 부분은 통과로 추정하지 않는다.

## 초보자를 위한 용어

- **배포**: 만든 코드를 사용자가 접근하는 환경에 반영하는 일이다.
- **릴리스**: 특정 버전을 사용자에게 제공하는 결정과 과정이다. 배포했어도 사용자에게 노출하지 않으면 아직 릴리스가 아닐 수 있다.
- **CI**: 코드가 바뀔 때 테스트와 빌드를 자동 실행하는 작업대다.
- **스모크 테스트**: 불을 붙이기 전 연기가 새는지 보는 것처럼, 배포 뒤 핵심 기능이 최소한 작동하는지 빠르게 확인하는 검사다.
- **롤백**: 문제가 생긴 새 버전을 이전 버전으로 되돌리는 일이다.
- **멱등성**: 같은 요청이 여러 번 와도 결제나 포인트가 한 번만 처리되는 성질이다.
- **헬스체크**: 서비스가 살아 있는지, 실제 요청을 받을 준비가 됐는지 확인하는 신호다.
- **관측 신호**: 로그, 오류 알림, 지표처럼 운영 상태를 알아차릴 수 있게 해주는 정보다.

## 먼저 지킬 원칙

- 기본은 읽기 전용 점검이다.
- 패키지 설치, 설정 변경, 시크릿 등록, 테스트 이벤트 발송, 부하 테스트, 데이터 변경, 실제 배포는 별도 요청 없이 실행하지 않는다.
- 시크릿이나 `.env` 값은 출력하지 않는다. 변수 이름, 대상 환경, 존재 여부만 확인한다.
- 파일이나 설정 항목이 있다는 이유만으로 실제 작동한다고 판정하지 않는다.
- 미리보기 주소가 열리거나 배포 도구가 성공을 반환해도 운영 환경의 핵심 기능이 정상이라는 뜻은 아니다.
- 운영 환경에 접근할 수 없으면 실패나 성공을 추정하지 않고 `확인하지 못함`으로 남긴다.
- 프로젝트에 없는 도구, 점수, 성능 기준을 임의로 추가하지 않는다.
- 사용자 데이터·금액·권한이 바뀌는 실제 테스트는 대상과 복구 방법을 확인하고 별도 승인을 받는다.

## 1. 점검 범위를 고정한다

이미 있는 정보는 다시 묻지 않는다.

```text
배포 대상 서비스:
대상 환경: 개발 / 미리보기 / 운영
배포할 버전 또는 변경 범위:
사용자가 영향을 받는 핵심 흐름:
바뀌는 설정·데이터·외부 연동:
실제 배포 포함 여부:
```

사용자가 환경변수나 오류 알림처럼 한 영역만 요청했다면 전체 감사를 덧붙이지 않는다.

## 2. 배포할 결과물을 확인한다

- 대상 환경과 같은 조건으로 만든 최신 빌드인가
- 필요한 테스트가 실제로 실행됐고 결과를 확인했는가
- 배포할 버전, 커밋, 산출물을 다시 찾을 수 있는가
- 개발 도구나 로컬 파일에만 의존하지 않는가
- CI와 로컬 명령이 서로 다른 패키지 관리자나 설정을 사용하지 않는가

테스트 일부만 통과했다면 실행한 범위만 보고한다.

## 3. 환경과 시크릿을 확인한다

- 필수 변수 이름과 대상 환경이 맞는가
- 개발·미리보기·운영의 데이터베이스, 저장소, 외부 API가 섞이지 않았는가
- 서버 전용 시크릿이 브라우저 코드나 공개 로그에 들어가지 않는가
- 키를 바꾸거나 만료시킬 방법과 담당자가 있는가
- 공급자 권한이 필요한 범위보다 넓지 않은가

실제 값을 화면이나 보고서에 복사하지 않는다.

## 4. 데이터 변경을 확인한다

스키마나 저장 데이터가 바뀔 때만 적용한다.

- 이전 코드와 새 데이터 구조가 함께 작동할 수 있는가
- 기존 데이터가 새 형식에서도 읽히는가
- 변경 중 일부만 성공했을 때 다시 실행해도 안전한가
- 삭제·변환 전 백업이나 검증된 복구 방법이 있는가
- 롤백하면 새 데이터와 이전 코드가 충돌하지 않는가

데이터 구조가 바뀐 뒤에는 코드만 이전 버전으로 되돌려도 복구되지 않을 수 있다. 이 경우 되돌리기 대신 안전한 추가 수정이 필요한지 구분한다.

## 5. 실패 동작을 확인한다

- 외부 요청이 끝없이 기다리지 않도록 제한 시간이 있는가
- 재시도가 같은 결제·예약·포인트를 중복 처리하지 않는가
- 웹훅이나 외부 알림의 발신자와 요청 내용이 검증되는가
- 부분 실패 뒤 사용자가 현재 상태를 알 수 있는가
- 내부 오류, 쿼리, 시크릿이 사용자 응답에 노출되지 않는가
- 실패가 조용히 사라지지 않고 담당자가 알아차릴 수 있는가

공개 업로드, AI 호출, 이메일 발송, 고비용 API가 있을 때는 요청량·파일 크기·동시 실행·비용 한도를 확인한다.

## 6. 감지와 복구를 확인한다

```text
무엇이 실패하면 알림을 받아야 하는가
어디에서 오류와 지표를 볼 수 있는가
누가 첫 대응을 하는가
언제 배포를 중단하거나 되돌리는가
되돌린 뒤 어떤 흐름을 다시 확인하는가
데이터 복구가 별도로 필요한가
```

로그는 행동에 필요한 정보만 남기고 개인정보, 인증정보, 결제 원문을 기본적으로 제외한다.

## 7. 배포 후 확인 계획을 만든다

배포 전 성공 기준을 정한다.

```text
서비스 첫 화면 또는 기본 응답:
가장 중요한 읽기 흐름:
인증이 필요한 대표 흐름:
데이터 저장이 필요한 대표 흐름:
외부 연동 흐름:
오류 알림과 지표:
중단·복구 조건:
```

실제 계정 생성, 결제, 이메일 발송, 운영 데이터 작성이 필요한 검증은 자동으로 실행하지 않는다. 승인된 테스트 계정·결제 수단·수신자와 정리 방법이 있을 때만 수행한다.

## 판정

- **배포 차단**: 필수 검증 실패, 필수 설정 누락, 데이터·권한·금액 손실 위험이 현재 증거로 확인됐다.
- **보류**: 중요한 항목을 확인하지 못했고, 실패하면 복구가 어렵거나 손실이 클 수 있다.
- **확인 범위 내 차단 요소 없음**: 확인한 범위에서는 차단 근거가 없다. 전체 안전 보장은 아니다.

가설만으로 배포 차단을 확정하지 않고, 중요한 미확인을 통과로 바꾸지도 않는다.

## 출력 형식

```markdown
## 배포 대상과 범위
- 서비스·환경·버전:
- 확인한 변경:

## 배포 차단 요소
- [근거와 영향, 없으면 확인 범위 내 없음]

## 확인된 준비 사항
- [직접 확인하거나 실행한 증거]

## 확인하지 못한 사항
- [접근 불가] 항목과 이유
- [이번 범위 밖] 항목과 이유

## 배포 후 확인
- 핵심 흐름:
- 감지 신호:
- 중단·복구 조건:

## 판정
배포 차단 / 보류 / 확인 범위 내 차단 요소 없음
```

## 초보자가 바로 쓸 요청 예시

```text
운영 배포 전에 준비가 빠진 게 없는지 점검해줘.
실제 배포는 하지 말고, 이번 변경에 해당하는 차단 요소와
확인하지 못한 부분을 구분해서 알려줘.
```

```text
환경변수가 운영에 제대로 등록됐는지 확인해줘.
값은 절대 출력하지 말고 변수 이름, 대상 환경, 존재 여부만 봐줘.
```

```text
배포 뒤 로그인과 예약 저장을 확인해야 해.
운영 데이터를 만들거나 실제 이메일을 보내는 단계는 실행하지 말고,
안전하게 확인 가능한 부분과 별도 승인이 필요한 부분을 나눠줘.
```
